Control 8 (auditd) - Detection Method Gotcha
==============================================

Initial baseline check used:
  which auditd

This returned "not found" and was recorded as before-auditd.txt, suggesting
auditd was not installed prior to Control 8.

However, after running harden.sh's install block, the script's own
dpkg -s auditd guard reported "auditd already installed, skipping" on its
FIRST run - meaning auditd was actually already present on the system
before this control was added, and the earlier "not found" result was
a false negative.

Root cause: 'which' only searches directories in the current user's $PATH.
auditd's binary lives at /usr/sbin/auditd, and /usr/sbin is typically only
included in root's PATH by default on Ubuntu - not a regular interactive
user's PATH. Running 'which auditd' as a non-root user (snehaadmin) will
report "not found" regardless of whether the package is actually installed,
because the shell never searches /usr/sbin in the first place.

Correct verification method going forward:
  dpkg -s <package>        (checks the package database directly, not PATH)
  apt list --installed | grep <package>

Lesson: 'which' is only reliable for confirming a binary is reachable in
the CURRENT PATH context - it should never be used to confirm whether a
package is installed at the system level. This applies especially to
daemons/services that live in /sbin or /usr/sbin, which regular users
often don't have in PATH by default.
