fail2ban Control 7 - Live Test Narrative
==========================================

Test setup:
- Terminal A: SSH session into web01-prod (snehaadmin@192.168.131.129)
- Terminal B: Fresh local PowerShell window (same host, IP 192.168.131.1)

Test steps:
1. Confirmed fail2ban not installed (before-fail2ban.txt)
2. Installed fail2ban, configured jail.local for sshd jail (maxretry=4, findtime=300, bantime=1800)
3. Discovered fail2ban defaults to systemd journal backend on this system rather than
   the logpath set in jail.local - updated config to explicitly set backend=systemd
   for clarity (matches actual behaviour rather than relying on auto-detection)
4. From Terminal B, deliberately triggered failed SSH logins:
   - ssh wronguser@192.168.131.129 (invalid user, repeated)
   - ssh -o PubkeyAuthentication=no snehaadmin@192.168.131.129 (forced auth failure)
5. After ~4 failed attempts within the 300s findtime window, fail2ban banned the
   source IP (192.168.131.1)

Result:
- Terminal B's next connection attempt: "Connection timed out" (banned at firewall level,
  SSH daemon never reached)
- Terminal A's existing session was also disconnected ("Connection reset") - because
  Terminal A and Terminal B share the same host IP, the ban blocked ALL SSH traffic
  from that address, including the legitimate admin session. This is expected fail2ban
  behaviour: it bans by IP, not by session or credential, so it cannot distinguish a
  legitimate admin and an attacker on the same network path.
- Confirmed via fail2ban-client status sshd after the 1800s bantime expired:
  Total failed: 4, Total banned: 1

Conclusion:
fail2ban successfully detected and blocked a simulated brute-force pattern against
SSH, demonstrating the control works as intended - including the realistic operational
trade-off that shared-IP admin access can also be affected by a ban.
